# CLAUDE.md

Guidance for Claude Code working in this repository.

## Project Overview

DevopsCoder is the implement-tagged work-item pipeline for our Azure DevOps automation suite. It is the first agent that writes to the target repo (branches, commits, push, draft PR). It deploys as a Docker container alongside the existing 4 read-only agents.

The repo is at the **milestone-11 stage** (Plans 1-8, 10-11 done): full end-to-end pipeline with cost and safety rails, operationally observable (per-WI cost + tool usage in the watcher log lines), and a real verification gate. After the analyzer accepts a WI, the orchestrator provisions a per-WI git worktree via `worktree-manager` (state-driven idempotent reuse off fresh `origin/main`), then runs `revisionLoop(coder, reviewer)` — the coder uses Claude with `Edit`/`Write`/`Bash` against the worktree, guarded by a strict Bash allowlist + path-escape filter, with retry-on-transient and per-attempt baseline reset on error. The reviewer is now real: 6 independent Claude agents run in parallel across axes safety-correctness, performance, code-structure, naming-style, security, and integration; findings are deduplicated by file:line and sorted severity-descending. `approved = !any(blocking|critical)`. If approved, the test-author writes tests, then the draft-PR creator pushes the branch and calls `ado.createPullRequest` to open a draft PR. On success the worktree is torn down; on failure paths the worktree is intentionally left for inspection. See `docs/superpowers/plans/2026-05-18-plan-5-reviewer-pr-teardown.md` for the Plan 5 design.

Plan 6 adds safety rails: `AgentRunner.run<T>` returns `{ value, costUsd, toolUsage }`; each LLM stage calls `tracker.add(stageName, costUsd)` to accumulate cost into `state.outputs.cost: PipelineCostInfo`; the orchestrator checks the cap before each top-level stage (`CostExceededError`) and wraps each stage in a `setTimeout` race (`StageTimeoutError`). The coder/reviewer run nested inside the top-level `revision-loop` stage, whose timeout defaults to `MAX_REVISIONS × (STAGE_TIMEOUT_MS_CODER + STAGE_TIMEOUT_MS_REVIEWER)` (pin with `STAGE_TIMEOUT_MS_REVISION_LOOP`). An `AbortSignal` is threaded through `PipelineContext.signal` per stage and forwarded to the runner and ADO client. External abort sets `state.cancelled` (resumable); cost-cap and timeout set `state.terminalError` with a formatted WI comment. See `docs/superpowers/plans/2026-05-19-plan-6-cost-safety-rails.md`.

Plan 7 ships the Docker deployment artifacts (`Dockerfile`, `docker-compose.example.yml`, README `## VM Deployment (Docker)`) and appends `(cost: $X.XX)` to the watcher's non-skipped outcome log lines. Plan 8 adds `tools: Edit×5, Bash×2` to the same lines — per-stage tool tallies (6 reviewer axes merged) accumulate in `state.outputs.toolUsage` via `createToolUsageTracker`.

Plan 10 adds the verification gate via `.tools/continia.exe` (wrapped in the injectable `ContiniaCli`, `src/services/continia-cli.ts`). `env-provision` (after worktree-setup) creates + starts a per-WI BC environment fire-and-forget — the 1-3 min boot overlaps the revision loop; environments are **never torn down** (DemoPortal auto-deletes after ~10 days) and the env URL lands in the PR description (`{{environment-id}}`/`{{environment-url}}`). `build-and-test` (after test-author) waits for Running, installs deps, discovers AL test codeunits (`Subtype = Test`), deploys each app in the deploy set (derived per WI; `CONTINIA_APP_PATHS` overrides), and runs every test codeunit sequentially; red results feed a bounded coder fix loop (`MAX_TEST_FIX_ATTEMPTS`, prompt `test-fixer.md`, same allowlist/reset machinery as the coder). Still-red throws `VerificationFailedError` (`'verification failed'` routes the processor's comment — checked BEFORE reviewer findings). Requires `CONTINIA_API_TOKEN` in env (required unless `SKIP_BUILD_TEST=true` — see Plan 11; `CONTINIA_ENV_PROFILE_ID` was required here too until Plan 12 made the profile derived per WI, leaving the pin an optional override); `CONTINIA_APP_PATHS` is an optional override that pins the deploy set, normally left unset because `build-and-test` derives it per WI.

Plan 11 hardens the verification gate against sibling-repo drift and adds WI-linked, Docker-deployable PRs. The deploy invocation is `continia deploy <envId> <absolute app dir> --allow-downgrade --json` from the worktree root — naming one app path is what scopes the run (deploy discovers siblings but builds only the app named), `--allow-downgrade` tolerates a lower-versioned reinstall, and `--with-deps` is deliberately NOT passed (it would recompile dependency apps unnecessarily). `--workspace-root` is deliberately NOT passed either: the CLI resolves the positional app path *against* workspace-root rather than cwd, so passing the same relative path in both slots joined it onto itself (`permission-sets/permission-sets` -> "No app.json found"), and scoping discovery to one app also hides the siblings the unpublished-dependency gate needs to see (see `.claude/skills/continia-deploy`). The app dir is passed absolute so the call does not depend on cwd. The Continia activation app (GUID `c3755ece-dab0-4d16-987d-040661f18522`) is auto-installed on the environment via `deps install-by-id` before any deploy; deps-install skip/symbol-gap counts (`DepsInstallInfo`) are logged as warnings rather than silently swallowed. Test-result parsing now uses a strict Zod schema — malformed CLI JSON throws instead of green-washing a run. `deployApp` reads the failure payload the same way `runTests` does: the CLI exits 1 on a failed deploy but still writes the per-app rows (carrying `code` and alc's full output in `error`) to stdout, so stdout is parsed BEFORE the exit code is judged — otherwise the only copy of why the build broke is discarded and a fixable red round becomes a terminal stage error. A run-level `{success:false,error:{...}}` object normalizes to one failed row. `findEnvironmentDeployFailure` then splits the two kinds of red: `compile-failed` / `compile-produced-no-app` / `publish-failed` (and any failed row with no `code`) are coder-fixable and feed the test-fix loop, while every other code (`unpublished-sibling`, `dependency-not-on-env`, `symbol-fetch-failed`, `app-lock-*`, …) is an environment problem that stops the stage immediately with the CLI's own message — no AL edit fixes those, so the fix loop would only burn attempts and misreport the cause. `CONTINIA_TEST_TIMEOUT_S` (default 600) is passed as `--timeout` to each `continia test run`. Draft PRs are now linked to their work item via `workItemRefs`, and the description is capped at `MAX_PR_DESCRIPTION_LENGTH` (4000 chars — ADO rejects longer descriptions with a 400) with the `## Test environment` section preserved and a truncation notice on earlier sections; `createdAt` comes from an injected clock and the abort signal is threaded through. Git auth is now per-invocation: `src/utils/git-auth.ts` builds an `http.extraHeader=Authorization: Basic ...` arg from the PAT for every fetch/push (never written to `.git/config`, so the origin URL should be credential-free) and redacts the PAT out of any git error text before it reaches logs or WI comments; pushes use `--force-with-lease`. `src/services/skill-wiring.ts` symlinks (junction, directories only, no-clobber) an orchestrator-owned skills tree into each worktree's `.claude/` when `SKILLS_SOURCE_DIR` is set, and skill advertisement merges target-repo + orchestrator skills with the target repo winning on name conflicts. `SKIP_BUILD_TEST` (default false) bypasses `env-provision` and `build-and-test` entirely for harness smoke runs, making `CONTINIA_API_TOKEN` optional. Docker changes: the Linux `continia` CLI binary is baked onto `PATH`, `/opt/al/bin` is bind-mounted read-only for the AL compiler, and `CONTINIA_AUTO_INSTALL_ALC=0` disables the CLI's own (broken) compiler auto-install in favor of that mount.

**Plan 12 derives the BC profile.** `env-provision` no longer creates every environment from a pinned `CONTINIA_ENV_PROFILE_ID`. It takes the highest `application`/`platform` across every `app.json` in the worktree, picks the lowest published profile version that satisfies it (`continia env profiles versions` / `list --bc-version`), and creates from the `CONTINIA_ENV_LOCALIZATION` profile (default `base`). The pin still overrides selection, but its environment is then validated and a mismatch throws. **Nothing is trusted because it was chosen carefully**: the catalogue rows are re-filtered against the requirement before the localization match (`--bc-version` is a server-side filter, and a row could come back off-version or carrying no version at all), a version/localization pair that publishes several enabled profiles picks the lowest id and warns, and the post-create `env get` check runs on the derived path too, not only the pinned one. The persisted-environment reuse path validates too, so a WI holding a stale environment recreates instead of reusing it forever — and an environment whose version **cannot be established** (no `bcVersion` from `env get`, none in the state file, which is every state file written before this plan) is likewise recreated rather than reused unchecked: a needless recreate costs a boot that overlaps the revision loop, a wrong reuse costs $33. The `ContiniaCli` additions are lenient in the way the rest of that file is: every new field is `.nullish()` (`.optional()` rejects an explicit `null`, which is what a .NET CLI emits for a nullable property), `envProfileSchema` requires nothing so one malformed row out of 18 cannot fail provisioning, and both profile-query parses rethrow a shape mismatch as a `ContiniaCliError` naming the argv rather than a bare `ZodError`. The pin was how WI 82205 got a BC 28.1 environment for a 29.0.0.0 branch and burned $33.16 before `build-and-test` reported it as `symbol-fetch-failed`.

**Plan 13 installs the localization app.** `build-and-test` deps-installs the country app matching `CONTINIA_ENV_LOCALIZATION` (`localizationAppDir`, `src/utils/al-app-graph.ts`; `base` → `banking-w1`, else `banking-<cc>`, falling back to `banking-w1` with a warning) **before** any deploy-set deps install. Since v29 the graph runs country-app → base-app and only the country apps declare `Continia Finance`, so dependency expansion from the deploy set can never reach one and Finance never arrived — WI 82205's deploy set had no country app and every deps install reported skipped deps and symbol gaps. The country app is deps-installed only and **never enters `appPaths`**: `external/Continia Finance/00_Base_App` declares the app.json name `Continia Finance`, so admitting a country app to the deploy set makes `resolveDeployOrder` compile vendored `application: 28.0.0.0` source against a BC 29 environment. `resolveDeployOrder` now also refuses to follow a dependency edge into `external/` at all, while still building a vendored app that was seeded directly. A repo with no country app logs and skips rather than failing the gate.

**Environments disappear before their expiry, and `env get` does not error when they do.** The Plan 10 note that environments are "never torn down (DemoPortal auto-deletes after ~10 days)" is wrong in the way that matters: WI 82205's environment was reclaimed on 2026-09-17 with an `expiresUtc` of 2026-09-29 — twelve days early. So a resumed work item finding its environment gone is an ordinary case, not an exotic one. It is also a silent case: `continia env get <deleted id>` returns **exit 0** with `"status": "Deleted"` rather than failing, so the `ContiniaCliError` branch in `env-provision`'s reuse path never fires. Before this was handled, the stage went on to call `startEnvironment` on a deleted environment, and `waitForRunning` — which knew only `Running` and `Failed` — polled it for the full 600s before timing out. `TERMINAL_ENV_STATUSES` (`src/services/continia-cli.ts`) is the shared list, deliberately a short set of what is *known* terminal (`Failed`, `Deleted`) rather than an allow-list of what is known transient: an unfamiliar status keeps polling, because a judgement that cannot be made must not block a run. Observed vocabulary: `Running`, `Stopped`, `Draft`, `Starting`, `Creating`, `Failed`, `Deleted`.

**Where agent-facing deploy knowledge goes.** The four `.claude/skills/continia-*` skills are **vendored upstream content shipped by the Continia CLI** — a CLI upgrade overwrites them in place, silently and without a merge conflict. Never put pipeline-specific guidance in them; it will disappear on the next upgrade and nobody will notice. `.claude/skills/devopscoder-al-deploy/` is the pipeline-owned home for that content, and it is a real channel rather than a documentation convention: the per-WI worktree is a checkout of the *target* repo with its own `CLAUDE.md`, so this file never reaches the coder — `skill-wiring` symlinking `SKILLS_SOURCE_DIR` is the only thing that does. A name upstream will never generate cannot be clobbered by an upgrade, so refreshing the CLI skills stays a pure overwrite with no diff to review. Keep this file as the orchestrator-developer view and the skill as the agent-facing one; cross-reference rather than duplicating verbatim.

**Per-step models (post-Plan 11).** Every LLM step resolves its model through `modelFor(config, step)` (`src/utils/model-selection.ts`) rather than reading `config.claudeModel`: `CLAUDE_MODEL_<STEP>` overrides one step, `CLAUDE_MODEL` is the fallback, and `config.stepModel` is the resolved record (steps: `analyzer`, `coder-plan`, `coder`, `reviewer`, `test-author-plan`, `test-author`, `test-fixer`, `pr-message` — note these are call sites, not `Stage.name`s). Naming a **planning** model (`CLAUDE_MODEL_PLANNING`, or `CLAUDE_MODEL_CODER_PLAN` / `CLAUDE_MODEL_TEST_AUTHOR_PLAN`) is also the on-switch for the plan-then-write split: the coder and test-author each first run a read-only plan call (`runPlanStep`, `src/pipeline/stages/_plan.ts` — tools `Read/Grep/Glob/Bash/Skill`, `Edit`/`Write` explicitly disallowed, read-only Bash allowlist, `PLAN_MAX_TURNS` turns, prompts `coder-planner.md` / `test-planner.md`) whose `PlanOutput` is rendered into the write call's prompt as `## Approved plan` / `## Approved test plan` and persisted to `state.outputs.coderPlan` / `.testPlan`. Deriving the gate from the model — instead of a separate boolean — keeps "which model plans" and "is there a plan step" from disagreeing, and leaves deployments that set no plan model on the previous one-call-per-stage behaviour. The coder re-plans when reviewer findings rejected the previous attempt (a stale plan would re-implement a rejected *approach*) but reuses a stored plan on a plain resume; the test-author plans once. Plan spend and tool usage are attributed to the `coder-plan` / `test-author-plan` cost keys, and `STAGE_TIMEOUT_MS_PLAN` is folded into the `revision-loop` (× `MAX_REVISIONS`) and `test-author` budget defaults only for stages that actually have a plan model. Nothing in `.claude/skills/**` pins a `model:`, so subagents a stage spawns inherit that stage's model — adding `model:` frontmatter to an agent file would silently override it.

**Spend attribution (post-per-step-models).** Cost is tracked by **LLM call site**, not `Stage.name`: `state.outputs.cost.perStage` is a `Record<string, StepSpend>` (`{ usd, calls, inputTokens, outputTokens, turns, models[] }`), keyed `analyzer` / `coder-plan` / `coder` / `reviewer:<axis>` (one key per axis, not one lumped `reviewer`) / `test-author-plan` / `test-author` / `test-fixer` / `pr-message` (the fixer nested in `build-and-test` and the message step nested in `draft-pr-creator` each bill to themselves, not to their stage). `AgentRunner.run` returns `usage: AgentUsage` alongside `costUsd`/`toolUsage`, and `tracker.add(step, usd, usage)` folds it in. `AgentUsage`/`StepSpend` carry **four** token counters, not two: `inputTokens` is only what the cache did *not* serve, so `cacheCreationInputTokens` and `cacheReadInputTokens` are where the bulk of a long agentic call's input actually lands — without them a real run logs `coder $4.8681 | 194 in / 61,226 out` and the dominant half of the bill is invisible. `renderCostReport` renders them as a `cache w / r` column plus a per-step `hit` rate (read ÷ all input), which is the number that says whether a step is re-sending a prompt it could be reusing. `normalizePerStage` widens state files written before the cache counters existed by zeroing them — `models` is a list because a resumed WI can legitimately span a model change. `normalizePerStage` (`src/utils/cost-tracker.ts`) widens a legacy bare-number map on read, so state files written before this still resume; it is applied both in `createCostTracker` and on the way into the ledger, so one ledger never carries two shapes. `src/utils/cost-report.ts` renders the two views: `formatSpendLine` (the watcher's `WI <id>: spend — coder $8.21, reviewer $4.02 ×6, …` line, sorted by spend descending, collapsing `prefix:sub` keys to `prefix $sum ×N` so the six reviewer axes stay one entry) and `renderCostReport` (the markdown cost table). `ProcessOutcome` carries `perStage` on every non-skipped variant so the watcher never reloads state to log the split.

**PR message (post-per-step-models).** The draft PR's title and description bullets come from a `pr-message` step nested in `draft-pr-creator` (`runPrMessageStep`, `src/pipeline/stages/_pr-message.ts`, prompt `pr-message.md`) — the automated port of the team's `/FinishWork:fw-step4-pullRequest` command in `.claude/commands/`. It is read-only (tools `Read/Grep/Glob/Bash`, `Edit`/`Write` disallowed, a read-only Bash allowlist, `PR_MESSAGE_MAX_TURNS` = 20) and runs in the worktree with `git diff <baseSha>..HEAD` as its only source of truth, following the command's own procedure: group hunks by logical change, one headline per group, then a validation checklist. **The separate call is the point.** Asking the coder for the same bullets at the end of a 20-turn session yields a description written from memory of that session, and the session leaks in — the failure that motivated this was a PR body narrating reviewer rounds, rejected alternatives and "no compile check was possible". A fresh context cannot narrate a run it never saw. The step is best-effort: on failure the stage logs and falls back to `coder.prBullets` → `coder.summary` + `testAuthor.summary` (bullets) and `coder.prTitle` → WI title, so a message failure never costs a pushed branch. `state.outputs.prMessage` is persisted, so a resume past this point does not pay twice, and `STAGE_TIMEOUT_MS_DRAFT_PR_CREATOR` defaults to 10 min (not 2) because the stage now contains an LLM call.

**Reviewer fan-out (post-per-step-models).** The six axes are hardened against one axis taking the whole stage down with it. **`ReportFindings` is on every structured-output stage's `disallowedTools`** (`STRUCTURED_OUTPUT_DENIED_TOOLS`, `src/pipeline/stages/_stage-helpers.ts`): it is the harness's own code-review reporting tool, it ships with the `claude_code` preset, and its contract is the inverse of ours — report through the tool and do *not* also print the findings — so a reviewer axis calls it and then signs off in prose (`Reported N findings.`), which reaches the runner as unparseable output. Each axis retries a malformed reply via `runWithParseRetry` (the same `MAX_TRANSIENT_RETRIES` the write stages use) instead of failing the revision loop on the first prose answer. The fan-out is `Promise.allSettled` over an internal `AbortController` chained to `ctx.signal`: **cost is billed per axis as it settles**, not after the fan-out, because a tracker call placed after `Promise.all` discards the spend of five finished axes the moment the sixth throws; a failing axis aborts its siblings so they stop billing against a stage that has already failed; and the first non-`AbortError` rejection is kept as `rootCause` so the cancellation an axis *caused* is never reported as the reason it failed. `AgentOutputParseError` carries the failed call's `spend` (`AgentSpend`: costUsd, toolUsage, usage) so retried attempts are billed too — a reply that fails to parse has still bought its tokens. Only the reviewer bills its failed attempts today; the coder, test-author, plan and pr-message retry loops still drop theirs.

**In-loop cost cap + entrypoint passthrough.** The orchestrator's cost gate is a *pre-stage* check, which is no help inside a stage that contains dozens of LLM calls: `revision-loop` holds `MAX_REVISIONS` x (1 plan + coder retries + 6 reviewer axes x retries), and nothing read the running total until it returned. WI 82205 entered that stage under a $20 cap and came back at $29.06. `assertWithinCostCap(state, cap, stageName)` (`src/utils/cost-tracker.ts`) now runs inside `revisionLoop` before *each half* of every round (the producer and the fan-out are each big enough to clear the cap alone) and inside `build-and-test` before each fix call. It throws the same `CostExceededError`, so the orchestrator records it against the stage that was actually running and the processor's `/cost cap/i` routing renders the usual comment. Note a WI already over cap stays wedged on resume by the pre-stage gate — raise `MAX_COST_USD_PER_WI` above the banked spend and restart, or `reset-state`. Separately, `entrypoint.sh` now passes its arguments through (`printf %q` quoted into the `su claude -c` string) instead of discarding them, so `docker compose run --rm devops-coder bun run src/cli/index.ts reset-state <id>` works; before, every documented operator command silently started the watcher instead.

**Reviewer severity ceilings.** `approved = !any(blocking|critical)` makes severity the loop-exit switch, and all six axes hold a copy of it — with `aggregateReviewerFindings` keeping a `file:line` group's *highest* severity, one inflated call decides a round alone. `AXIS_SEVERITY_CEILING` (`src/pipeline/stages/reviewer.ts`) caps what each axis may assign: `safety-correctness`/`security` → `blocking`, `integration` → `critical`, `performance`/`code-structure` → `major`, `naming-style` → `minor`. The clamp runs **before** aggregation (a ceiling applied after the merge could be re-breached by a co-located finding) and is keyed on the axis that actually ran, never the model-supplied `axis` field — that field is part of what is being policed. Clamps are logged. The case that motivated it: WI 82205 spent $23.95 over three rounds and died on one `critical` reading "diverging from established codebase idiom", raised jointly by `safety-correctness` and `naming-style`, while the other four findings were one `major` and three `minor`. `reviewer-shared.md` already classified pattern violations as `major` and already warned against over-flagging — the prompt said so and the model did it anyway, which is why the rule now lives in code. The rubric there additionally requires a `blocking`/`critical` finding to name a concrete failure, and fixes "diverges from the established idiom/convention/pattern" at `major`. Retune the table rather than the barrier.

**Tool permissions (post-cache-accounting).** The SDK draws three lines and the project was using one of them for all three: `tools` is the base set of built-in tools that *exist* for a call, `allowedTools` is the set auto-approved *without* consulting `canUseTool`, and `disallowedTools` is removed from the model's context outright. Every stage's tool list was passed as `allowedTools`, so it restricted nothing and auto-approved everything. `buildQueryOptions` now passes it as `tools` (only when the stage supplied one — `tools: []` disables every built-in tool, where the old `allowedTools: []` harmlessly auto-approved nothing), and omits `allowedTools` entirely whenever a `canUseTool` is present, since anything auto-approved there is a tool the filter never sees. Note stages list `'Skill'` in that set and the SDK deprecates `'Skill'` in `allowedTools` in favour of a separate `skills` option; skills are expected to keep working through `tools`, and a run where the coder suddenly cannot invoke `continia-deploy` is the signal that they do not. `buildQueryOptions` also sets `permissionMode: 'default'` whenever the stage passes a `canUseTool`, and only falls back to `'bypassPermissions'` (plus `allowDangerouslySkipPermissions`) when it does not. This is load-bearing, not tidying: under `bypassPermissions` the SDK auto-approves every call *before* the callback runs — it warns `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` once per call — so the coder's Bash allowlist and `createPathEscapeFilter`, i.e. the whole of the worktree containment, were dead code in production while `disallowedTools` was the only rule with teeth. A real WI's tool tally showed `AskUserQuestion×1, ToolSearch×1, ReportFindings×1` for tools that appeared in no stage's `tools` list. `ALWAYS_DENIED_TOOLS` (`AskUserQuestion`, `ToolSearch`) is merged into `disallowedTools` for *every* call in the runner rather than per stage — a deny rule is the one control that survives any permission mode, and `AskUserQuestion` in an unattended container burns a turn waiting for an answer that cannot come. The Docker entrypoint also chowns `LOG_DIR` to `claude`: it is a host-owned bind mount, and without the chown every per-WI log write fails `EACCES` and the run's cost table is lost.

**Per-WI log files.** `src/services/wi-log.ts` writes `<LOG_DIR>/WI<id>.log` (default `logs/`, bind-mounted in Docker). `createLogger(prefix?, sinks?)` takes `LogSink`s that receive the *already formatted* line, so the file is byte-identical to the console and cannot drift. `createProcessor` takes an optional `wiLogs: WiLogFactory`; `processWorkItem` opens the WI's log and calls `makeInner(wiLog.logger)` — the inner object is a factory whose `logger` parameter **shadows** the outer one, which is what threads the WI-scoped logger through every call site (including `buildPipeline`) without passing it by hand. Each open appends a `=== run <ts> ===` separator rather than truncating, so a resumed WI keeps the cycle that banked most of its spend; `recordSpend` closes the file with `renderCostReport`. Writes are best-effort and warn once per factory — a log that cannot be written must never fail a run. Dry runs get neither the ledger nor the log files.

## Architecture

- **Runtime:** Bun (TypeScript)
- **Validation:** Zod for env config and agent output schemas
- **AI:** `@anthropic-ai/claude-agent-sdk` — `query()` is wrapped in an injectable `AgentRunner` interface (`src/pipeline/agent-stage.ts`). `AgentRunner.run<T>` returns `{ value, costUsd, toolUsage }` — cost and tool usage are first-class. The production runner (`src/services/claude-agent-runner.ts`) uses the `claude_code` system prompt preset with a JSON-only structured-output instruction appended, then validates the result against the per-stage Zod schema. Supports `cwd`, `disallowedTools`, `maxTurns`, `canUseTool`, `settingSources`, `systemPromptAppend`, `signal` for per-stage tuning.
- **Markdown:** `marked` for rendering reject-comment markdown into HTML for ADO comment posts.
- **Testing:** `bun:test`
- **State:** per-work-item JSON files under `.state/{workItemId}.json`
- **Pipeline:** stage-based orchestrator. Each stage is a `Stage` (`name`, `canRun`, `execute`). Stages signal flow via three error sentinels: `PipelinePauseError` (halt and wait), `PipelineRejectError` (analyzer says WI isn't ready — populates `state.rejection`), or a regular `Error` (terminal failure). The only stage factory is `revisionLoop`; all concrete stages are hand-rolled (each needed bespoke flow — branching, retries, or fan-out). Full 8-stage chain (6 when `SKIP_BUILD_TEST=true`, which drops `env-provision` and `build-and-test`): `[analyzer, worktree-setup, env-provision, revisionLoop(coder, reviewer), test-author, build-and-test, draft-pr-creator, worktree-teardown]`.

## Key patterns

- **Dependency injection** via interfaces on every external dep (logger, AgentRunner, state store, ADO client when added).
- **Per-WI state** persisted after every stage transition; a `PipelinePauseError` from a stage signals "halt and wait for human" rather than a terminal error.
- **Test fixtures** built with small factory functions (`makeContext`, `makeState`) and `bun:test`'s `mock(...)`.
- **Conventions:** `.ts` extensions in imports (`verbatimModuleSyntax: true`); `type` imports use the `type` keyword.

## Commands

- `bun test` — run all tests
- `bun run typecheck` — TypeScript type checking
- `bun run start` — start the long-running watcher
- `bun run once` — single poll cycle, prints cycle stats as JSON
- `bun run src/cli/index.ts run-wi <id>` — process one work item by ID
- `bun run src/cli/index.ts reset-state <id>` — delete `.state/{id}.json`
- `bun run src/cli/index.ts debug-tags` — list WI IDs tagged with `TRIGGER_TAG`
- `bun run src/cli/index.ts debug-pr <id>` — print the draft-PR record stored in state for a WI
